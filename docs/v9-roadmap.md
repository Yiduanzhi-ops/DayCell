## 一、背景与目标

DayCell 是纯前端 PWA（GitHub Pages 托管、数据在用户本地），目前约 **270 个真实用户**，经小红书引流。现状痛点：

- 无账号 → 认不出用户、无法运营、无法收费
- 数据锁在单设备 → 换机即丢（用户最大恐惧）
- 无推送 → 待办/习惯提醒全靠用户自己打开才看到
- 无 AI → 差异化弱
- 无分析 → 不知道真实活跃/留存/付费转化

**v9 目标：给 DayCell 长出一个"后端底座"，让产品从"免费玩具"变成"能收费、能运营、有差异化"的成熟产品。**

核心原则（贯穿全版，三条铁律）：

1. **本地永远是数据源头（Source of Truth）**——云端是同步/备份层，绝不覆盖本地
2. **同步方向唯一：本地 → 云端**（首次登录上传）
3. **后端挂了 → 静默降级回本地模式**，用户无感，数据无损

### 1.1 当前主线总览（双主线并行，2026-10-25 定案）

**主线 A · 纯前端产品完善（阶段一，主攻）**
- 目标：拉日活、强留存——把"试了一下"变成"天天用"
- 内容：v9.0 到点本地通知 + 连续记录激励 → v9.1 年度报告/数据洞察 + 分享图 → v9.2 文本/Excel 智能导入（本地规则版）；穿插常规 bug 修复
- 手段：纯前端，零后端、零成本、可立即开工
- 成功标准：日活/留存数据上来（先产品内本地统计观察，后续埋点验证）

**主线 B · 后端与付费服务探索（阶段二，低强度并行）**
- 目标：验证"有后端的产品值不值钱"，为收费铺路
- 内容：① 自行体验后端（CloudBase 免费环境 + 本地前端，真机用 1-2 周）② 选型拍板（后端/邮件/AI API/定价/PAYDAY）③ 云同步免费验证需求 ④ 条件成熟再动工开发
- 手段：零线上接触（不推 main），本地 + 免费环境，随时可弃
- 成功标准：体验结论 + 选型清单 + 需求验证数据

**两条主线的关系（协同不互斥）**
- 主线 A 产出日活 → 主线 B 的付费才有地基（先让人离不开，再谈收钱）
- 主线 B 的结论反过来决定主线 A 之后的方向（后端值不值 → 要不要大改）
- 时间分配：开发精力主攻 A（每周 5-8h）；B 以碎片时间探索（注册、体验、看定价），不抢占 A

**贯穿红线（两条主线都必须遵守）**
1. 发布纪律五关：自动化全绿 → 本地起服务亲手点通 → 才部署 → 线上抽查 → 大功能 Feature Flag + 灰度
2. 只增不改：现有功能路径一行不改，新增功能独立分支
3. 老用户永远免费（模型 A），收费日由数据决定

## 二、后端选型（已讨论，倾向 CloudBase）

| 方案 | 国内速度 | 免费档 | 决策 |
|---|---|---|---|
| **腾讯云 CloudBase（云开发）** | ✅ 快（国内节点） | 有免费额度（认证+数据库+云函数） | **主选** |
| Supabase 官方云 | ❌ 跨境延迟不稳 | 500MB 免费 | 仅开发测试可用 |
| Supabase 自托管 | ✅ | 需租服务器 | 暂不采用（运维成本） |
| 阿里云 Serverless | ✅ | 按量 | 备选 |

**选择理由**：国内用户产品必须国内节点；CloudBase 的"认证 + 数据库 + 云函数 + 存储"与 Supabase 一一对应，架构可平移，切换成本低。

**免费额度评估**：存储每用户几百 KB~1MB（1000 用户 ≈ 1GB）；API 每人每天 20-30 次。**几百到两三千用户免费档够用**；超限时每月几十元成本，可由会员收入覆盖（成本结构健康）。

**能力对应关系**（后端能力 → 产品功能）：

| 后端能力 | 支撑的功能 |
|---|---|
| 认证 Auth | 账号登录、付费身份、老用户判定 |
| 数据库 | 用户数据存储、事件埋点表 |
| 云函数 | 付费验证、AI 代理、推送发送、定时任务 |
| 存储 | 备份文件 |

## 三、账号体系（已定：可选门，不强制注册）

- **不做"打开即要求登录"的用户体系**；登录只在用户主动开启云同步时出现
- 登录形态：**邮箱免密登录（Magic Link）**——输邮箱 → 收邮件点链接 → 登录完成（无用户名密码，链接 15 分钟有效）
- 老用户（不登录）使用体验与现在**完全一致**，界面不出现登录入口
- 真实小麻烦：邮件可能有 1-2 分钟延迟/进垃圾箱 → 所以绝不把登录做成"必经的门"，只能作为可选功能

## 四、云同步（v9.0 核心功能）

### 4.1 数据模型

**整包 JSON 快照**：每次改动后把完整数据存一条云端记录（DayCell 数据几百 KB，整包同步最简单，天然复用现有备份 JSON 形态）。不做逐条 CRUD（冲突逻辑少 80%）。

### 4.2 同步策略

- 启动时自动拉取（云端新 → 合并到本地）
- 改动后防抖推送（几秒后静默上传）
- 冲突处理：时间戳对比，后改生效（或简单合并，复用已有 merge 引擎经验）
- 首次登录：本地数据全量上传（方向唯一）
- 失败降级：断网/后端故障 → 静默退回本地模式，恢复后自动补齐

### 4.3 用户流程（三场景）

**场景一 · 首台设备开启同步：**
```
菜单 → 同步设置 → 「开启云同步」（会员/试用判断）
→ 邮箱登录（输邮箱→点邮件链接）
→ 「正在同步…」→ 本地数据全量上传 → 「同步完成 ✓」
→ 此后全自动，无任何手动操作
```

**场景二 · 日常使用：** 打开自动拉取，改动自动推送，用户无感知（可选右上角绿点=已同步）。

**场景三 · 换手机/新设备：**
```
新手机打开 DayCell（空白）→ 同步设置 → 登录（同邮箱）
→ 「正在恢复数据…」→ 云端数据下载合并 → 全部恢复
→ 文案：已从云端恢复 N 条记录
```

| 功能 | 卖点 | 依赖后端 | 优先级 |
|---|---|---|---|
| **云同步/多端** | 换机数据自动恢复 | ✅ | v9.0（地基） |
| **推送提醒** | 待办到期/习惯打卡/复盘提醒 | ✅ Web Push | v9.1 |
| **AI 智能导入** | 文本/Excel 自动拆条成待办 | ✅ API 代理 | v9.2 |

| 年度报告 | "今年完成 486 个待办"传播点 | 本地可算 | v9.4（可选） |

**会员权益包叙事**：输入（AI 导入）→ 管理（DayCell）→ 提醒（推送）→ 总结（AI 回顾），覆盖用户全链路。

### 5.1 推送提醒（Web Push，PWA 即可，不需要 App）

- 平台支持：安卓 Chrome（装主屏幕）✅ 完整；桌面 Chrome/Edge ✅；iOS Safari 16.4+ ✅（需装主屏幕+授权）
- 机制：用户授权 → 浏览器生成订阅凭证 → 存后端 → 到期后端发推送（云函数）→ 浏览器弹通知（App 未打开也能收到）
- 前提：需用户点"允许通知"；关机/断网收不到（App 同理）

### 5.2 AI 智能导入（文本 / Excel）

**文本场景**：微信/群消息复制一段话 → 打开 DayCell → 粘贴 → AI 解析成结构化 JSON `[{标题, 日期, 归属模块(待办/习惯/目标), 优先级}]` → **预览确认页**（可勾选/修改）→ 导入。

**Excel 场景**：上传 Excel → 结构识别（长表/宽表/自由文本）→ 字段归一化（日期多格式/合并单元格前向填充）→ 预览确认 → 导入。

**铁律：解析结果必须预览确认，绝不静默写错**（低置信度条目单独标注待确认）。

**交互限制（诚实声明）**：PWA 收不到微信"分享到 App"；入口 = 复制 → 打开 DayCell → 粘贴 → 解析（多一步，可用）。

**付费逻辑**：每次解析消耗 token（真成本）→ 免费用户每月小额限额当钩子，会员不限量/大量。

### 5.3 AI 周/月回顾

- **否决本地模型方案**：WebGPU 在 iPhone Safari 支持差（用户约一半是 iPhone），本地跑不现实
- **采用云端 API**：DeepSeek/豆包 API + 后端代理（key 不能放前端，否则被白嫖）
- 免费用户手写复盘，会员一键生成；按月限额防滥用
- 技术细节：AI key 存后端环境变量，云函数转发

## 六、数据分析体系（后端的"眼睛"）

**埋点原则**：事件埋点 + 聚合统计，**不读用户内容**（守住"只看统计不看内容"规矩）。

**三张表起步：**

```
users          用户表：注册时间、来源渠道（?source=xiaohongshu/pwa）、付费状态
events         事件流水表：user_id、事件名、时间、附加参数
               （打开App、添加待办、完成待办、打卡、写想法、写复盘、开同步…）
subscriptions  付费表：付费时间、金额、到期时间
```

**可回答的问题**：DAU/WAU 真实活跃、注册次日/7日/30日留存、功能热度分布（决定开发资源投向）、访问→注册→试用→付费漏斗、渠道效果（小红书 vs 直接访问）、续费预警。

## 七、收费模型（已定案：模型 A · 祖父条款）

```
老用户 = daycell-first-visit < 收费日  →  永久免费（不判断试用）
新用户 = daycell-first-visit ≥ 收费日  →  30 天试用从首访起 → 到期收费
```

- 埋点已上线：`daycell-first-visit`（v8.58/v8.59，幂等不覆盖）✅

- 市场先例背书：Obsidian（本地优先+同步付费）、Notion/Figma（祖父条款）、滴答清单（免费基础+会员）
- **收入预期**：270 用户 × 15% 转化 ≈ 40 人付费，短期几百~两三千/年；真正增长在用户破千破万后

**定位提醒**：差异化不是"比滴答清单多几个功能"，而是"极简 + 本地优先 + 真隐私 + 无广告"。

## 八、变现路径论证（整体买断 vs 免费+会员，已定案：不买断）

**背景**：用户提出简化方案——"不做会员、所有现有基础功能整体收费、一次性买断"（理由是后端/会员功能太复杂、本质赚钱靠用户数）。

**深度分析结论：不采用整体买断**，理由五条：

1. **付费墙前置 = 掐死用户数**（用户数即增长引擎）：
   - 免费+会员：无门槛 → 一年累计 ~3600 人 × 5% 转化 × 25 元/年 ≈ 4500 元/年，且逐年滚
   - 整体买断：付费墙砍掉 ~95% 潜在用户 → 一年 ~180 人 × 0.5-1% 转化 ≈ 几十~千元，一次性
2. **买断 = 一次性收入**：第二年收入归零；个人产品要持续迭代，没有持续现金流走不远
3. **无账号 = 用户失联**：买断用户连"谁买的"都不知道，无法通知升级/客服/召回
4. **买断承诺锁死**：收了"永久"钱，以后加任何付费功能 = 二次收费（名声受损）；不加 = 无新收入
5. **本地优先产品特殊性**：买断适合"一次性交付"的工具；DayCell 是"天天用、持续迭代"的生活工具，付费买的应是持续服务关系

**复杂度治理（用户核心顾虑）**：答案不是退回整体收费，而是**只做一个付费功能起步**：
```
v9.0 = 云同步一个会员功能（后端底座+邮箱登录+同步），复杂度最小
AI/推送按排期慢慢加，不做"一次性全上"
```
可选的最低成本验证：**"8 元解锁云同步扩展包"**（不叫会员），看有没有人掏钱——有人掏=模式成立，没人掏=免费再跑一阵。用数据验证，不用整体收费赌。

## 九、成本与维护风险管理（2026-10-25 讨论）

### 9.1 云同步成本算账（结论：成本永远追不上收入）

- **本地优先架构红利**：免费用户数据在本地 → 不用云 → 后端成本 = 0；只有付费用户（用云同步）产生云端成本 → **成本和收入天然同源**
- 量级：每用户几毛/月 vs 会员 25 元/年 → **毛利 90%+**
- 即使转化率崩了，最多是"收入低"不是"亏到肉"

### 9.2 CloudBase 免费档评估（用户已传定价截图，结论：免费档只够个人 Demo）

- 免费档：¥0/月，每月 **3,000 资源点**，仅 1 个免费环境
  - 量级：只够 3-10 个用户轻度用一个月；270 用户付费部分（20-30 人）是它的几十倍
  - **致命点：免费档"暂不支持资源包与按量付费"= 超限直接停服**（不是降速是中断）——对付费用户是信任事故
- 个人版：¥19.9/月（限时优惠），40,000 资源点 + **超限按量（不中断）** + 余额告警 + 99.95% SLA
- **成本策略**：
  - 开发期 → 免费档（就自己连，够用）
  - 灰度期（3-5 人）→ 继续免费档观察
  - 正式开放 → 买 19.9 个人版；**10 个付费用户即覆盖全年成本（240 元/年）**

### 9.3 被骂的真相与四层保险（化解"维护不好被骂"恐惧）

**用户骂点真相**：骂的是"开发者消失 / 数据丢 / 过度承诺画饼"，**没人骂"功能太多"**——本地优先架构已解"数据丢"，剩两个用下面四件套解：

```
护城河 = 本地优先（数据永远不丢） + Feature Flag（坏能关）
       + 版本回滚（坏能回） + 少承诺（预期管好）
```

**维护成本分级**（决定开发顺序）：

| 功能 | 维护成本 | 备注 |
|---|---|---|
| 云同步（整包快照） | 低-中 | 逻辑简单，后端托管，出 bug 好修 → **先做** |
| 推送提醒 | 中 | 依赖系统 API，结构简单 |
| **AI 功能** | **高** | API 会变、效果不稳、token 花钱 → **最后做或标"实验性"** |

### 9.4 AI 成本防滥用设计（用户恐惧：用户往死用 token → 被迫关掉 → 被骂）

**被骂的不是"功能关了"，是"承诺了无限却收回"**。解法：从第一天就卖"有限"：

1. **额度明示**：会员页写"AI 周回顾 · 每月 30 次"——用户购买时就知额度，用光不骂人
2. **Beta/实验标签**：明示"可能调整、可能下线"，实验功能宽容度高
3. **条款留口**：会员协议写"AI 额度可能随成本调整，调整前 30 天公告"，老用户不涨不砍
4. **技术防线**：按用户限额、输入裁剪（只送摘要）、便宜模型（DeepSeek 档）、结果缓存、用量告警熔断

**算账**：一次周回顾 ≈ 1000 token ≈ 0.01-0.05 元；每月 30 次 ≈ 0.3-1.5 元成本 vs 25 元/年会员费 → **成本占比 1-6%，毛利 90%+**。限额在，AI 成本可控，根本走不到"关掉"那步。

**AI 功能三形态（择一，绝不卖"无限"）**：① 会员有限额度（每月 N 次）② 按次明码标价（每次 0.5 元 / 6 元 20 次额度包）③ Beta 声明随时调整。

## 十、隐私与合规（已决策：明文存储）

**决策**：不做端到端加密，**明文存储**（开发者能看到数据），原因是用户要运营能力（统计、客服恢复）。

**必须遵守的三条规矩**：
1. **不卖数据**（红线，碰了就是刑事：侵犯公民个人信息罪）
2. **不主动看内容**（只看聚合统计，不点开单个人）
3. **防护做到位**：HTTPS 传输加密、数据库强密码、密钥不进代码、访问控制仅管理员、异常提醒

**宣传口径调整**：
- 原："你的数据只属于你" → 改为："数据本地保存，云同步加密传输；无广告、不卖数据、不看你的内容"
- 与会员分层的叙事：**安全永远免费**（本地存储+免费导出），会员买的是"多端同步的便利"（自动无感），不是"安全"
- 免费用户也可通过手动导出/导入实现换机恢复——"数据还在"是免费的，会员差异是"自动还在"

**法律风险认知**：被动泄露罚的是"未尽到保护义务"；主动出售 = 刑事。按目前规模（270 用户、生活记录、非敏感信息）实际风险很低，做好四条防护即可。

**遗留提醒**：将来用户破万如需"极致隐私"差异化，可在架构上加端到端加密层（上传前加密，随时可加，不是回头路）。

## 十一、增长与用户获取（三引擎，2026-10-25 讨论）

**前提认知**：个人产品没有"自然流量"，增长只能靠三个引擎——**内容获客 × 传播裂变 × 留存复利**；"稳定用户"不是推出来的，是**留出来的**。

**引擎 1 · 内容获客（小红书已验证，放大）**

从"偶尔发帖"升级为**内容体系**（每周固定节奏 2-3 条）：

| 内容类型 | 例子 | 作用 |
|---|---|---|
| 迭代日记 | "DayCell 新功能：AI 导入" | 老用户回来看 + 新用户围观 |
| 场景种草 | "考研党怎么用 DayCell 管住每天" | 垂直人群转化 |
| 干货引流 | "复盘到底怎么做" | 内容有用，顺手带产品 |
| 个人叙事 | "我一人写了款 App，270 人用" | 独立开发故事天然有传播力 |

小红书跑通后**复制到多平台**：抖音/B 站（30 秒演示视频）、知乎（干货长文）、即刻/微信群，渠道 1 → 3-4 个。

**引擎 2 · 传播裂变（让现有用户帮忙拉人）**

产品内做**"替用户传播"的设计**（用户分享的动机是"晒自己"，产品被顺带传播）：
- **年度报告分享图**（最有传播性）："2026 年我完成了 486 个待办、打卡 21 天"——用户发朋友圈/小红书 = 免费广告
- **模板分享**：每日模板生成分享链接，别人一键套用
- **成就卡**：连续坚持 30 天生成打卡成果图

**引擎 3 · 留存复利（"稳定用户"的真正答案）**

| 留存钩子 | 对应 v9 功能 |
|---|---|
| **数据积累**：记录越久越离不开 | 云同步"换机不丢"（v9.0，最大留存钩子） |
| **每日触达**：每天回来形成习惯回路 | 推送提醒（v9.1） |
| **成就激励**：不舍得断的沉没成本 | 连续记录徽章/文案 |

**复利路径**：`270 →（内容+传播）→ 1000 →（口碑+留存）→ 3000 → 5000+`；前 6 个月最难，每月稳定增长 20-30%，一年约 10 倍。

**时间分配（个人开发者现实）**：产品迭代每周 5-8 小时（v9 功能一个一个上）；内容每周 2 条固定产出（节奏比数量重要）；传播设计随产品迭代顺手做（年度报告这类）。

**一句话公式**：稳定用户 = **留得住 + 内容不断 + 用户帮你传**，缺一不可。270 个现有用户是先发资产——先服务好他们，比推新用户更值钱。

## 十二、测试与发布流程（已讨论定案）

**核心思路：把"上线代码"和"开放功能"分开（Feature Flag）**

```
① 本地隔离测试：npm run dev + 本地后端实例，完整走通注册→同步→换机
② 部署上线：新版前端上线，但功能默认"锁死"（开关默认关闭，入口不可见）
③ 后门自测：https://…/DayCell/?dev=1 打开开关（或自己账号自动激活）
④ 灰度：稳定后开放给 3-5 个核心用户 → 观察 1-2 周
⑤ 全量：放开开关
回滚预案：git revert + 重推，30 分钟回旧版
```

**其他用户"误触"的三层隔离**：
1. 开关默认关 → 入口不可见（第一层）
2. 后端数据按账号隔离 → 误用也不污染他人（第二层）
3. 本地为源 + 回滚 → 最坏是同步失败，本地无损（第三层）

**动工前准备**：代码埋 `featureFlag` 机制（常量/远程开关）+ 约定 `?dev=1` 后门。

## 十三、执行优先级重估（2026-10-25 重要战略更新）

**触发点**：用户自我质疑——"云同步需求没那么大，用户只要数据不丢，日活不高，有这个需求的人更少"。

### 13.1 两个关键洞察

1. **"数据不丢"是高频焦虑，"多端同步"是低频需求**：
   - 用户真实需求 = 怕换手机/清缓存数据没了 → 手动导出/导入已部分解决（免费）
   - 云同步 = "自动不丢"的保险，但用户一年也就换一次手机 → **保险的付费意愿远低于日用品**
2. **日活低才是真瓶颈**：270 人用过但天天打开少 = "试了一下"不是"离不开" → **没有日活，任何付费功能都是空中楼阁**。先解决"每天回来"，再解决"回来的人付费"

### 13.2 战略转向：先拉日活（纯前端），后端验证后再上

**近期主线 = 纯前端高价值功能**（零后端、零成本、直接拉日活）：

| 功能 | 技术 | 作用 |
|---|---|---|
| **到点本地通知** | Notification + Service Worker | 待办/习惯到点提醒，每天把你叫回来 |
| **连续记录激励** | 本地统计 | "已连续记录 N 天"徽章，沉没成本 |
| **年度报告/数据洞察** | 本地数据计算 | 晒图分享 = 传播 + 留存 |
| **语音播报** | Web Speech | 趣味性，"每天打开"的理由 |
| **文本/Excel 智能导入（规则版）** | SheetJS 本地解析 | 降低输入成本（免费 MVP） |

**后端推迟**到"用户证明离不开"之后（日活/留存数据说话）。云同步如需验证需求：**先免费开放 2 个月** → 用的人多再收费；没人用直接关（**免费功能下线无痛，付费功能关闭才伤信任**）。

### 13.3 后端独有能力清单（纯前端做不到，验证后值得上）

| 能力 | 纯前端 | 说明 |
|---|---|---|
| **Web Push**（App 未打开也推送） | ❌ 本地通知仅页面存活时有效 | 叫回用户的终极手段 |
| **AI 回顾/智能导入**（云端模型） | ❌ iPhone WebGPU 兼容差 | 最值钱的高级感 |
| **事件埋点统计** | ❌ 只能看自己 | 第一次真正"看见"用户：DAU/留存/功能热度/漏斗 |
| **公开分享页** | ❌ 只能生成本地图片 | 年度报告分享链接 = 增长放大器 |
| **付费验证/会员权限** | ❌ 本地标记可绕过 | 真正收钱的门 |
| **照片云备份** | ❌ 见 13.4 | 解决 iOS 清理风险 |

### 13.4 图片存储路线（用户问：后端存图有优势吗）

**纯前端存图的限制**：localStorage ~5MB 上限；IndexedDB 有配额（几百 MB~2GB）；**iOS Safari 对 PWA 的 7 天未访问清理策略——照片可能"悄悄没了"，这是纯前端硬伤**。

**结论**：
- 后端存图优势真实（对象存储/CDN：容量按 GB、不占设备空间、CDN 加载快、消除 iOS 清理风险）——但**存对象存储不是存数据库**（数据库只存 URL）
- 权衡：照片是最私密的数据，上云 = 与"本地优先/隐私"卖点冲突；且图片是体积之王，免费白嫖不起
- **最优路线**：
  ```
  主力：本地 IndexedDB 存原图 + 压缩缩略图（单张压到 200-500KB，几百张几十 MB，够用）
  付费：照片云备份（会员功能）——"照片默认本地，云备份需主动开启"，保险卖点
  ```
- 照片云备份比文本同步更好卖：**iOS 用户真的怕丢照片**

### 13.5 自行体验后端（零风险方案，动工前建议先做）

```
① 注册 CloudBase → 创建免费环境（3000 资源点，就自己用绰绰有余）
② 初始化认证 + 数据库（控制台点几下）
③ 前端本地连云端：.env.development 把 SDK 指向云端环境 → npm run dev
④ 自己真机体验 1-2 周：注册邮箱、登录、记数据、换设备看数据在不在
   → 感受"有后端"的 DayCell 长什么样、同步什么体验、统计能看见啥
```

**零风险保证**：不推 main = 用户零感知（线上仍 v8.59）；免费环境不花钱；体验完不满意 → 控制台删环境，一切归零。**用爽了 → 有底气推进 v9；没感觉 → 删环境省掉后端，也不亏**。

## 附：关键结论速查

**后端与架构**
- 后端 = 账号 + 数据映射之外，还有付费验证/AI 代理/推送/统计/远程配置/分享页 6 类能力
- BaaS/Serverless 与"租服务器"的区别：运维谁管、钱怎么花；本阶段用免费档 BaaS 即可
- GitHub Pages 不换、用户不迁移、网址不变——后端是"叠加层"不是"替换"
- BaaS 技术栈：前端 TS 不动、调后端用官方 SDK、云函数用 TypeScript（前后端同语言、类型共享）；BaaS 内部语言是黑盒，与用户无关
- 本地优先+仅同步需登录 = 成熟品类（local-first），Obsidian/Logseq/Bear 验证；核心免费+同步付费是标准打法

**收费与变现（已定案）**
- 收费模型 A：老用户（首访 < 收费日）永久免费；新用户 30 天试用从首访起 → 到期收费；`daycell-first-visit` 埋点已上线
- **拒绝整体买断**：付费墙前置掐死用户数 + 一次性收入归零 + 无账号失联 + 买断承诺锁死；坚持"免费核心 + 单付费功能起步"
- 云同步成本每用户几毛/月 vs 25 元/年，毛利 90%+；免费用户零后端成本（本地优先红利）
- **CloudBase 免费档只够个人 Demo**（3000 资源点 + 超限即停服不支持按量）；正式开放买 19.9 个人版（超限按量不中断），10 个付费用户覆盖年费
- 会员叙事三件套：同步（数据不丢的便利）、AI（懒得写的解放）、推送（老忘的提醒）
- 云同步上线流程：先免费开放 2 个月验证需求 → 数据好再收费；免费功能下线无痛

**风险与维护**
- 被骂真相：数据丢 / 过度承诺 / 开发者消失，不是功能多；四层保险 = 本地兜底 + Feature Flag + 回滚 + 少承诺
- 维护成本分级：云同步低-中（先做）、推送中、AI 高（最后做/标实验性）
- AI 防滥用：额度明示 + Beta 标签 + 条款留口（30 天公告）+ 技术限额（裁剪/便宜模型/缓存/熔断）；成本占比 1-6%；**绝不卖"无限"**

**战略（2026-10-25 更新）**
- 日活低 = 真瓶颈：先拉日活（纯前端功能优先），后端等"用户证明离不开"再上
- 后端独有能力：Web Push / AI 云端 / 事件统计 / 公开分享页 / 付费验证 / 照片云备份
- 图片存储：本地 IndexedDB + 压缩缩略图（主力），照片云备份做付费功能（对象存储不是数据库）；iOS 7 天清理是纯前端硬伤
- 自行体验后端：CloudBase 免费环境 + 本地前端指向云端，自己真机用 1-2 周，不推 main 零风险，随时可删
- 增长三引擎：内容获客（小红书体系化+多平台）× 传播裂变（年度报告/模板/成就卡分享）× 留存复利（提醒/激励/云同步）
- 发布纪律（五关）：自动化全绿 → 本地起服务亲手点通 → 才部署 → 线上抽查 → 大功能 Feature Flag 默认关 + 灰度；后端物理隔离（不推 main = 用户零感知）
- **当前双主线（见 1.1）**：主线 A 纯前端完善（拉日活，主攻）‖ 主线 B 后端与付费探索（选型/体验/验证，碎片并行）；红线 = 五关发布纪律 + 只增不改 + 老用户永远免费
