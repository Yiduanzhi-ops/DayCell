# ADR-0004 农历库懒加载与降级

- **状态**：已接受
- **日期**：2026-09-29
- **相关**：PRD §5.1 / E4 / E14、ADR-0002、CORE-API §5.3

## 背景

农历、节气、传统节日是这个产品的差异化要素之一（格子里的标签位、纪念日按农历重复），必须有。

但唯一可靠的离线库 `lunar-typescript` **约 80 KB**——它内置了 1900–2100 年的农历表、24 节气算法和节日数据。这个数字比整个应用自己的代码（约 15 KB gzip）还大。

而 PRD §5.1 的首屏预算是 **≤ 80 KB gzip**，React 已经吃掉约 45 KB。**如果农历库进首屏包，预算直接爆掉。**

## 决策

### 1. 动态 import，独立分包

`lunar-typescript` 只能通过 `core/lunar.ts` 里的 `await import('lunar-typescript')` 引入。**任何模块禁止静态 import 它**（ESLint `no-restricted-imports` 强制）。

构建产物中它是一个独立 chunk，由 Vite 自动 hash 命名，并被 Workbox 纳入 precache（ADR-0002）。

### 2. 整个 lunar 模块的入口是异步的

```ts
function loadLunar(): Promise<LunarApi>;
```

UI 在启动时调一次，拿到 `LunarApi` 后**同步**使用（`lunarOf(k)` 是同步纯函数）。这样只有"加载"是异步的，42 次标签计算不会变成 42 次 await。

### 3. 失败自动重试 1 次，仍失败则抛 `LunarUnavailableError`

### 4. 降级：只显示公历，绝不白屏

```ts
// UI 层
const lunar = await loadLunar().catch(() => null);   // null = 不可用
// core/label 接受 null
cellLabel(k, lunar?.lunarOf(k) ?? null, anniversaryTitles)
// → { text: '', kind: 'none' }，标签位留空
```

**降级时的行为约定**：
- 格子标签位留空，日期数字与所有记录内容**完全正常**
- 不弹错误框、不打断用户
- 顶部显示一条可关闭的浅色提示"农历信息加载失败，将在下次打开时重试"
- 农历纪念日**当天不显示**（无法换算），但纪念日的公历日期仍正常

## 理由

**为什么必须懒加载**：80 KB 在首屏是纯粹的性能税。农历信息是**渐进增强**——没有它，DayCell 仍然是一个完整的记录应用；有了它，格子上的信息更丰富。这种"锦上添花"的东西不该阻塞首次可交互。

**为什么会加载失败**（不是假想，是必然会遇到的场景）：
1. **发版后旧页签**：用户三天前打开的页签还挂着旧 HTML，此时懒加载去请求 `lunar.abc123.js`，而服务器上只有 `lunar.def456.js` → 404。这是 SPA 的经典问题，ADR-0002 的"不立即激活新 SW"缓解了一部分，但覆盖不到已经卸载 precache 的情况
2. **弱网 / 地铁 / 电梯**：首次访问时 chunk 请求超时
3. **`*.pages.dev` 域名被 DNS 污染**（PRD Q4 提到的部署风险）：主文档能拿到但静态资源被干扰

**为什么重试 1 次而不是 3 次**：404 和 DNS 污染不会因为多重试几次就好；弱网场景 1 次重试已经覆盖。多次重试只会拖长失败判定、让降级提示迟迟不出现。

**为什么不预取（preload）**：Vite 的 `modulepreload` 会让浏览器在空闲时提前拉这个 chunk，看起来两全其美。但它会**与首屏关键资源抢带宽**，在国内弱网下反而拖慢 TTI。折中做法：在 `requestIdleCallback` 里手动触发 `loadLunar()`，首屏渲染完成后再加载。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|---|---|
| 静态 import，进首屏包 | 爆掉 80 KB 预算，首屏多约 30 KB gzip 与一次额外解析 |
| 换更小的农历库（如 `chinese-lunar-calendar` ≈10 KB） | 只算农历日，**不含 24 节气与传统节日**，而节气（白露/秋分）和节日（中秋）恰恰是格子里最有价值的标签。省 70 KB 换掉核心功能不值 |
| 自己实现农历算法 | 农历是**天文历法**，节气要算太阳黄经，靠公式近似会有 ±1 天误差；1900–2100 的闰月表也得内置。这是典型的"看起来简单、做起来是坑"，且错一天用户立刻能发现 |
| 构建时预生成 2025–2027 的静态 JSON | 体积确实小（约 15 KB），但**只能覆盖预生成的年份**，农历纪念日换算到 2030 年就失效。而且用户翻页翻到范围外就露馅 |
| 接在线农历 API | 违背 PRD §5.4"运行时零网络请求"，且离线不可用 |

## 后果

**正面**
- 首屏 gzip 约 62 KB，留出余量
- 农历加载失败不影响任何核心功能
- 发版导致的 chunk 404 从"白屏"降级成"少了农历标签"

**负面**
- **首屏渲染时格子标签位是空的**，农历加载完成后才填上，会有一次视觉跳变。**缓解**：`requestIdleCallback` 预取 + 首屏渲染前 `await` 一个 200 ms 的短超时（命中缓存时几乎总是同步完成）
- 多一个异步边界，UI 需要处理 `lunar === null` 的分支。**缓解**：`cellLabel` 的签名强制传 `LunarInfo | null`，类型系统保证不会漏
- 测试要 mock 加载失败路径

## 实施要点

- `loadLunar()` 结果**缓存到模块级变量**，只加载一次；失败结果不缓存（下次启动重试）
- 重试之间加 500 ms 退避，避免瞬时网络抖动下两次请求挤在一起
- 用 Vite 的 `manualChunks` 显式命名为 `lunar`，便于在构建报告里盯住它的体积
- **基准测试**：CI 里断言首屏 chunk 总和 ≤ 80 KB gzip，超了直接失败
- 农历表覆盖范围 1900-01-01 ~ 2100-12-31，超出时 `lunarOf` 返回空信息而不是抛错（PRD E14）
- 节日**白名单**在 `core/lunar.ts` 内部实现（PRD D15）。`lunar-typescript` 会返回"全民国防教育日""世界住房日""万圣节前夜"这类噪音，不过滤会占满格子——原型阶段实测过这个问题
