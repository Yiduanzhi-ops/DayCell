# ADR-0001 本地存储：IndexedDB + 记录级存储 + 软删除

- **状态**：已接受
- **日期**：2026-09-29
- **相关**：PRD §6、ADR-0006、CORE-API §4

## 背景

DayCell v0 是纯前端应用，无后端。数据必须存在浏览器本地，同时满足三个约束：

1. 目标容量 **10 年 / 约 4 万条记录 / 约 18 MB**（PRD §5.2），`localStorage` 的 5 MB 上限直接出局
2. 月视图要在 100 ms 内渲染，**不能把全库读进内存**
3. v1 可能加云同步（PRD Q5）。**如果 v0 的存储结构不是同步友好的，将来要重写整个存储层**

第 3 条是本决策的真正驱动力。同步友好的结构有两条硬规则，事后补不进去。

## 决策

用 IndexedDB，并遵守三条不可违背的规则：

### 1. 记录级存储，不做"一天一个 blob"

每条待办 / 想法 / 花费都是**独立记录**，各自带 `date` 字段。

```
❌ days: { '2026-09-29': { todos:[...], notes:[...], expenses:[...] } }
✅ todos:     { id, date:'2026-09-29', text, done, ... }
   expenses:  { id, date:'2026-09-29', amountCents, catId, ... }
```

### 2. 软删除（墓碑），永不物理删除

删除 = `put({...rec, deleted: true, updatedAt: now})`。
**`RecordStore` 接口里根本没有 `remove` 方法**——用结构而非约定来强制。

### 3. 每条记录必有 `updatedAt`

冲突策略 = 记录级 last-write-wins。**不引入 CRDT**。

### 库结构

数据库 `daycell`，6 个 store：`todos` / `notes` / `expenses` / `anniversaries` / `categories` / `settings`。
内容 store 各建 `byDate(date)` 与 `byUpdated(updatedAt)` 索引。

## 理由

**为什么记录级**：blob 模型下，手机加了条待办、电脑记了笔花费，同步时两边各持有"完整的 9/29"，合并只能整天覆盖——**必丢一边的数据**。记录级则各改各的，天然无冲突。

**为什么软删除**：物理删除的记录在同步时会**复活**——对端不知道它被删了，下次同步又推回来。墓碑是唯一可靠的做法。代价是库会缓慢膨胀，但一条墓碑约 150 字节，10 年删 1 万条也才 1.5 MB，可忽略。

**为什么 LWW 不用 CRDT**：单用户、多设备、非协作场景。同一时刻在两端改同一条记录的概率极低，且改了也无非是"以较新的为准"。CRDT 的复杂度（Yjs/Automerge 约 30–60 KB + 心智负担）完全不值。

**为什么 6 个 store 而不是一个大 store**：三类内容访问模式不同——花费要按分类聚合、待办要过滤 `rolledTo`。分开后类型安全，查询不需要 `[type, date]` 复合索引。代价是月视图要发 3 次范围查询（CORE-API 的 `byDateAll` 在**同一个只读事务**里并发发出），毫秒级，可接受。

**为什么留 `byUpdated` 索引**：将来增量同步只需游标扫这一个索引。现在建索引的成本几乎为零，事后加索引要走 `onupgradeneeded` 迁移。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|---|---|
| `localStorage` + JSON | 5 MB 上限；同步 API 阻塞主线程；无索引，月视图必须全量解析 |
| SQLite WASM（`sql.js` / `wa-sqlite`） | 查询能力强得多，但 WASM 包 300 KB–1 MB，且 OPFS 在 iOS Safari 16.4 才可用、持久性仍有坑。v0 的查询复杂度用不上 SQL |
| 一天一个 blob（`DayEntry`） | 同步时整天覆盖，必丢数据。**这是 SPEC §5 的旧模型，已废弃** |
| 直接上云端（Supabase / CF D1） | 需要账号体系与后端，v0 明确不做；且引入网络依赖会破坏"离线 100% 可用"和红线 1 |
| 不做同步预留，将来重写 | 存储层是重写成本最高的部分。现在多花的力气（墓碑 + `updatedAt` + 索引）不到 1 天工作量 |

## 后果

**正面**
- 月视图 = 3 次索引范围查询（约 350 行），与库总量无关，10 年数据仍是毫秒级
- v1 加同步时，只需新增一个 `SyncAdapter` 与 `byUpdatedSince` 的消费方，**repo 层以上零改动**
- 导出/导入天然按记录合并，不会产生"整天覆盖"的灾难

**负面**
- 库会因墓碑缓慢膨胀（量级可忽略，见上）
- 每个读路径都必须显式过滤 `deleted`。**缓解**：过滤在 `RecordStore` 实现里统一做，repo 层拿到的已经是干净的；需要墓碑的场景（导出、同步）走 `all()` 或 `includeDeleted: true`
- 6 个 store 意味着一次"写一天"可能要开多个事务。**缓解**：`rollOver` 这类跨 store 操作用 `store.tx()` 包成单事务

## 实施要点

- IndexedDB 原生是回调式 API，用 `idb`（约 1.2 KB）做 Promise 封装。**不要手写 `onsuccess` 链**
- iOS Safari 的 IndexedDB 明显慢于 Chrome：**批量写必须走单事务**，禁止在循环里逐个 `put`
- `put()` 必须自动刷新 `updatedAt`，不依赖调用方传——漏传会破坏 LWW
- `estimateStorage()` 要定期采样，接近配额时提前提示（PRD E2），而不是等写入失败
- 迁移必须是**纯函数**且能被导入流程复用（PRD E18：导入旧版本备份）
